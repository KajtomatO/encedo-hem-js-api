# HEM firmware 1.2.2: HTTP header names are matched case-sensitively

Report to Encedo, 2026-10-07. Reporter: (fill in).

## Summary

The HEM's HTTP server recognises request header names only in one exact
spelling (`Content-Length`, `Content-Type`, `Authorization`). A request whose
header names are spelled in any other case — for example the all-lowercase
names that HTTP/2 mandates and that several HTTP/1.1 clients also emit — is
treated as if the header were absent:

- a `POST` whose `Content-Length` arrives as `content-length` is answered
  with **411 Length Required**;
- a `POST` whose `Content-Type` arrives as `content-type` (with a correctly
  spelled `Content-Length`) is answered with **413**;
- a request whose `Authorization` arrives as `authorization` is processed
  **as if it carried no token** (200 on a public endpoint instead of the 401
  a present-but-invalid token gets).

RFC 9110 §5.1 ("Field Names") makes field names case-insensitive, so clients
are free to choose the case. The practical consequence: **Node.js cannot use
the API through its built-in `fetch`** — Node's HTTP client (undici) always
writes the `Content-Length` it generates as `content-length`, and does not let
an application override it — so every request with a body fails with 411.
Encedo's own `hem-sdk-js` (https://github.com/encedo/hem-sdk-js) already
works around this on Node by sending requests that carry a body through
`node:https` with an explicitly spelled `Content-Length` (its comment
attributes the 411 to chunked encoding; the measurements below show it is
the header-name case).

## Observations

All requests below differ only in the spelling of header names. Status codes
as returned by the device.

### `POST /api/auth/token` with body `{"auth":"x"}` (a deliberately invalid proof)

| Header names sent | Status | Expected per RFC 9110 |
|---|---|---|
| `Content-Type` + `Content-Length` | 401 | 401 (invalid proof) |
| `content-type` + `content-length` | **411** | 401 |
| `content-type` + `Content-Length` | **413** | 401 |
| `Content-Type` + `content-length` | **411** | 401 |

### `GET /api/system/status` (a public endpoint)

| Header sent | Status | Expected |
|---|---|---|
| none | 200 | 200 |
| `Authorization: Bearer junk` | 401 | 401 (present, invalid token is rejected before routing, as documented) |
| `authorization: Bearer junk` | **200** | 401 |

### `GET /api/keymgmt/list` (a protected endpoint)

| Header sent | Status |
|---|---|
| none | 401 |
| `Authorization: Bearer junk` | 401 |
| `authorization: Bearer junk` | 401 |

(On a protected endpoint both spellings give 401 — "missing" and "invalid"
look the same — which is why the public endpoint above is the telling case.)

### From a browser

From Chromium on the device's own origin (`https://my.ence.do`), the same
requests behave as expected (401 / 401 / 200): browsers write header names
in their canonical capitalised form. libcurl does the same. This is why the
Encedo Manager web UI and libcurl-based clients are not affected.

### What Node.js puts on the wire

Captured with a local HTTP server (`req.rawHeaders`), Node.js v24.21.0,
built-in `fetch` (undici):

```
POST /post
    host: 127.0.0.1:34177
    connection: keep-alive
    Content-Type: application/json      ← caller's spelling is kept
    Authorization: Bearer t             ← caller's spelling is kept
    accept: */*
    ...
    content-length: 12                  ← generated by undici, always lowercase
```

undici's lower-level `request()` behaves the same way, and it discards a
caller-supplied `Content-Length` in favour of its own lowercase one. Against
the device this yields 411 for every request with a body; a `GET` with a
caller-spelled `Authorization` works.

## Reproduction with curl

```sh
U=https://my.ence.do

# Authorization: the lowercase spelling is ignored (200 instead of 401).
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer junk' $U/api/system/status   # 401
curl -s -o /dev/null -w '%{http_code}\n' -H 'authorization: Bearer junk' $U/api/system/status   # 200

# Content-Length: curl replaces its own header when one with the same name
# is given, so the lowercase spelling can be forced.
curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'Content-Type: application/json' \
     -H 'content-length: 12' --data '{"auth":"x"}' $U/api/auth/token                             # 411
# The same request with curl's default `Content-Length: 12` answers 401
# (observed with an equivalent raw request; the curl run itself was cut
# short by the stall noted below).
```

## Reproduction with Node.js

```js
// Node.js 24, no dependencies. Expected 401 (invalid proof); observed 411.
const r = await fetch('https://my.ence.do/api/auth/token', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: '{"auth":"x"}',
});
console.log(r.status); // 411
```

## Related observation: keep-alive

Successful responses carry `connection: keep-alive`, but the device closes
the TCP connection after the response anyway. A client that honours the
header and reuses the socket (Node's default `https.Agent` since Node 19)
fails its next request with `ECONNRESET` ("socket hang up"). Either sending
`Connection: close` or keeping the connection open would make the two
consistent.

## Note on the test session

After roughly forty probe requests over about four hours of uptime the
device stopped answering entirely (a `GET /api/system/status` timed out) and
needed a power cycle — the sustained-load stall already known from the C
client's testing.

## Suggested fix

Compare request header names case-insensitively (RFC 9110 §5.1), at least
for `Content-Length`, `Content-Type`, `Authorization`, `Origin` and
`Content-Disposition`. Until then, every client that cannot control the case
of its `Content-Length` header — notably anything built on Node's `fetch`,
and any HTTP/2-style client — cannot send a request with a body.
